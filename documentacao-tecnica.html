01 · CONTEXTO

Visão geral

O sistema centraliza cadastros, atividades, distribuição e aprovação de horas, tarifas, análises operacionais e autosserviço do colaborador.

UI

Aplicação administrativa

Páginas HTML compartilham o shell e os componentes de primorely-plain.js.

API

Serviços de domínio

Rotas PHP organizadas por recurso e CRUD compartilhado com mapeamento app/banco.

DB

Persistência relacional

MySQL armazena colunas operacionais e payload JSON para compatibilidade evolutiva.

02 · ARQUITETURA

Camadas e responsabilidades

Navegador

Renderização, validações, modais, filtros e chamadas HTTP.

→

Endpoints PHP

Autorização, regras de negócio, transações e respostas JSON.

→

MySQL

Cadastros, direcionamentos, horas, sessões, auditoria e configurações.

Contrato de respostaEndpoints devem responder JSON, inclusive em erros. Uma resposta HTML indica rota incorreta, redirecionamento do host ou falha antes do controlador.
03 · CÓDIGO

Estrutura do projeto

/ # páginas administrativas /assets # CSS e JavaScript compartilhados /img # identidade visual /api/_shared # banco, CRUD, autenticação e regras comuns /api/auth # autenticação administrativa /api/portal-colaborador # sessão e operações do colaborador /api/analises # aprovação, rejeição e histórico /api/apontamentos # lançamentos administrativos /api/relatorios # datasets e exportações

Convenção frontend

Cada HTML define data-page. O shell identifica o módulo e carrega dados pela API.

Convenção backend

Recursos CRUD usam crud_handle(); processos especiais possuem controladores próprios.

06 · DOMÍNIO

Fluxos críticos

Criar direcionamento

Definir tarifa, gestores, total preventivado e ao menos um colaborador.

Distribuir horas

O total da atividade é a referência; cada colaborador recebe uma parcela controlada.

Lançar ou solicitar

O portal valida vínculo e saldo antes de gravar. Solicitações seguem para Análises.

Aprovar e sincronizar

A decisão atualiza os totais, preserva histórico e aparece no portal.

07 · PROTEÇÃO

Segurança e acesso

  • Sessões administrativas por token e expiração por inatividade.
  • Rate limiting nos logins administrativo e do colaborador.
  • Escopo por gestor ou acesso global conforme usuário.
  • Senhas armazenadas como hash; credenciais não devem entrar no frontend.
  • Operações compostas devem usar transação e rollback.
  • Documentação pública não carrega sessão nem expõe dados internos.
08 · OPERAÇÃO

Publicação segura

Configurar ambiente

Definir conexão MySQL e parâmetros do servidor fora do repositório público.

Validar alterações

Testar autenticação, CRUD, direcionamento, portal, horas e exportações.

Publicar arquivos

Enviar o estado validado, preservar configurações do host e limpar caches estáticos.

Smoke test

Confirmar login, dashboard e respostas JSON das rotas mais críticas.
